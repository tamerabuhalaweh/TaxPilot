- **(a) Phase 1 carve-out: APPROVE narrower scope conditionally.** Phase 1 delivers catalog + legal_entities + obligations/registrations + tax_contexts + JO manifest + confirmation + resolver contracts, explicitly PARTIAL against full 8-object JUR-01 scope (no `business_presences`, no `tax_groups` schema or tests, no portfolio orchestration). Opt-in suggestion only (§3); no-engagement backfill deferred as a future conditional migration.
- **(c) Neutral `ACCOUNTING_ONLY` scope code, separate from statutory tax types.** A confirmed accounting-only review requires user-provided entity + period only, tolerates UNKNOWN registration, and never asserts incorporation, registration, obligation, or treatment. Any initial JO statutory `tax_type_code` list stays subject to accountant/tax-expert input (DEC-04/10).
- **(d) Encrypted-from-day-one.** Ciphertext storage model below (§6) whenever identifier collection is enabled; no plaintext interim or fallback. If key management is not implemented, sensitive registration writes stay disabled behind an explicit fail-closed gate.

## 1. Objective
Unblock JoFotara reconciliation preparation with the smallest schema + contracts that (a) satisfy Master §6 for a Jordan-only happy path, (b) cannot accidentally execute non-JO rules, and (c) leave multi-country depth as clean follow-ups.

## 2. Scope: Phase 1 vs deferred (explicit)
- **Phase 1 (this proposal):** `jurisdiction_catalog` + `legal_entities` + `tax_obligation_profiles` + `tax_registrations` + `tax_contexts` + JO pack manifest seed (metadata only); context create/confirm/freeze + `ACCOUNTING_ONLY` scope; capability read APIs; confirmation-gated behavior; resolver contracts testable today.
- **Deferred to Phase 2:** `business_presences`, `tax_groups` + memberships, Tax & Countries full UX (JUR-03 beyond a minimal entity picker), portfolio orchestration, EP-16 RAG implementation, subnational zones.
- **Rationale:** the JO happy path needs no presence/group rows; adding them now widens review surface without an executable consumer. Recorded as a PO-approved partial delivery against FR-JUR-002/004 and full JUR-01 — not as completed implementation.

## 3. Migration `0004`: empty tables, zero fabricated facts (correction A)
- Creates the five Phase-1 tables + catalog/manifest seeds ONLY. **Zero `INSERT … SELECT` from `clients`; zero invented legal entities, obligations, or TaxContexts.** Existing client rows remain byte-identical except the additive constraint in §4.
- Opt-in onboarding suggestion (UI/onboarding proposal ONLY, separate from migration): when an accountant starts a JO review for a client with no entity, the UI MAY pre-fill a suggestion draft (country JO pre-selected) that persists ONLY after the user explicitly enters legal identity + country + currency + tax period/type and confirms. A suggestion draft, if persisted at all, lives in a clearly-marked non-executable draft state (`confirmation_status='DRAFT'`, never confirmable without all required fields) and MUST NOT generate obligations or contexts.
- Engagement-linked backfill is a FUTURE conditional migration (no engagements table exists; nothing to backfill). Tests assert: existing client counts unchanged; zero `legal_entities`/`tax_obligation_profiles`/`tax_contexts` rows created by migration; UNKNOWN permitted on read paths, never auto-REGISTERED or auto-NOT_REGISTERED.

## 4. Executable constraints (correction B)
Additive `0004` changes to existing tables (old migrations never edited):
- `ALTER TABLE clients ADD CONSTRAINT clients_tenant_id_key UNIQUE (tenant_id, id);` — the candidate key PostgreSQL requires before any composite FK may reference it.
- New-table keys and constraints:
  - `legal_entities`: PK `(id)`; `UNIQUE (tenant_id, id)`; `UNIQUE (tenant_id, client_id, legal_name)` where active (partial index on `status='active'`); `FOREIGN KEY (tenant_id, client_id) REFERENCES clients (tenant_id, id)`; `FOREIGN KEY (incorporation_country_code) REFERENCES jurisdiction_catalog (code)`; `FOREIGN KEY (tenant_id, parent_legal_entity_id) REFERENCES legal_entities (tenant_id, id)` (same-tenant hierarchy); `CHECK (base_currency ~ '^[A-Z]{3}$')`; indexes on `(tenant_id, client_id)` and `(tenant_id, incorporation_country_code)`.
  - `tax_obligation_profiles`: PK `(id)`; `UNIQUE (tenant_id, id)`; `FOREIGN KEY (tenant_id, legal_entity_id) REFERENCES legal_entities (tenant_id, id)`; `FOREIGN KEY (jurisdiction_code) REFERENCES jurisdiction_catalog (code)`; `CHECK (valid_from <= valid_to OR valid_to IS NULL)`; `CHECK (registration_status IN ('UNKNOWN','NOT_REGISTERED','PENDING','REGISTERED','ENDED'))`; index `(tenant_id, legal_entity_id, jurisdiction_code)`.
  - `tax_registrations`: PK `(id)`; `UNIQUE (tenant_id, id)`; `FOREIGN KEY (tenant_id, obligation_profile_id) REFERENCES tax_obligation_profiles (tenant_id, id)`; `CHECK (number_ciphertext IS NULL OR (number_nonce IS NOT NULL AND key_id IS NOT NULL))`; index `(tenant_id, obligation_profile_id)`.
  - `tax_contexts`: PK `(id)`; `UNIQUE (tenant_id, context_hash)` (tenant-scoped; global uniqueness REJECTED); `FOREIGN KEY (tenant_id, client_id) REFERENCES clients (tenant_id, id)`; `FOREIGN KEY (tenant_id, subject_entity_id) REFERENCES legal_entities (tenant_id, id)`; `subject_group_id UUID NULL WITHOUT FK in Phase 1` + `CHECK` allowing only `subject_kind='LEGAL_ENTITY'` with entity set and group NULL (group subjects unlock with the Phase 2 table + FK — the CHECK is written so Phase 2 widens it, never a permanently non-null entity FK blocking groups); `FOREIGN KEY (jurisdiction_code) REFERENCES jurisdiction_catalog (code)`; `CHECK (period_start <= period_end)`; `CHECK (confirmation_status IN ('DRAFT','NEEDS_CONFIRMATION','CONFIRMED'))`; index `(tenant_id, client_id, jurisdiction_code, period_start)`.
- A one-column FK to a globally unique id is NOT accepted as tenant isolation anywhere above: every cross-table reference carries `(tenant_id, …)` and is covered by different-client/different-tenant negative SQL tests.
- Confirmed-context immutability (no dynamic per-row REVOKE — REJECTED): `BEFORE UPDATE` trigger `tax_context_freeze_guard()` raises on ANY change to frozen columns (`subject_*`, `jurisdiction_code`, `tax_type_code`, `regime_code`, `obligation_profile_id`, `profile_version`, `period_*`, `pack_version`, `snapshot`, `context_hash`) once `OLD.confirmation_status='CONFIRMED'`; new revisions are INSERTs with `context_revision+1`. Status-only bookkeeping on confirmed rows is forbidden — supersession is a new row.
- Migration safety: `migrate.py` gains (as specified implementation work) `pg_advisory_xact_lock()` single-migrator serialization, a `CHECKSUMS` manifest (sha256 per migration version, verified before apply, mismatch aborts), and forward/rollback tests (apply → row-count reconcile → rollback → re-apply clean). Controlled single-migrator deploy policy ships with the implementation PRs (per #36, before multiple domain migrations).

## 5. ACCOUNTING_ONLY scope and snapshot contract (correction C)
- Scope codes: `ACCOUNTING_ONLY` (neutral, non-statutory — confirmable below) vs statutory `tax_type_code` values (initial JO list explicitly UNDECIDED pending DEC-04/10; no code may invent one).
- `ACCOUNTING_ONLY` confirmation requires: user-provided legal entity identity (explicitly entered, never inferred), jurisdiction JO, descriptive review period (user-entered start/end; no default dates), and user confirmation. It tolerates `registration_status=UNKNOWN` and NULL `obligation_profile_id`/`profile_version`. It MUST render a no-compliance-claim banner and permit ONLY approved deterministic accounting/REC capabilities — of which zero are executable today, so confirmed `ACCOUNTING_ONLY` contexts exist without executing anything until EP-07/15 land (stated plainly; no capability implied).
- Transitions: `DRAFT → NEEDS_CONFIRMATION → CONFIRMED`, atomic, authorization-checked (confirm endpoint re-validates all required fields per scope against live rows; concurrent confirms serialize on the row lock; double-confirm is idempotent success). Any confirmed-field change mints a new UUID revision (supersession chain); no in-place mutation of confirmed rows (see trigger, §4).
- Frozen snapshot: `snapshot` JSONB holds EVERY confirmed value (tenant, client, subject kind+id, jurisdiction, scope/type codes, obligation id+version or explicit nulls, period, revision, pack version, confirmer + time, `snapshot_version: 1`); `context_hash = sha256` over the canonical serialization (UTF-8 JSON, lexicographic keys, no whitespace, uppercased codes, lowercase UUIDs, ISO dates). Hash verifies integrity; never authorization.
- `ExecutionSnapshot` (context hash + dataset/mapping/rule/pack versions + inputs, write-once at enqueue) is specified here as a FUTURE artifact — no jobs carry contexts yet, so no worker verification exists to test; its contract tests land with the first executing worker (#35 gate).

## 6. Registration security and pack gating (correction D)
- Ciphertext storage model: `number_ciphertext BYTEA` (AES-256-GCM) + `number_nonce BYTE(12)` UNIQUE per value (random 96-bit, never reused) + `key_id TEXT` + `alg_version TEXT default 'aes-256-gcm-v1'` + immutable AAD bound as `tenant_id || registration_id || field-name`; `last4` stored separately for display/search. Encrypt-before-persist inside the data-access layer (service code never sees plaintext at rest); masked reads (last4/authority/status only) for all roles; raw values only in the creating/updating request scope, never logged, never in URLs/exports/audit payloads (values excluded; access events recorded). Grants: create Owner/Admin; masked read for assigned roles; decrypt-access audit entries. Key provider: KMS/env-managed DEKs resolved by `key_id`, rotation with dual-read window + re-encryption job, rotation policy (90 days or on suspicion) — concrete provider choice follows ADR-001 hosting (DEC-03). Key-missing/unavailable → fail closed (503 `PACK_NOT_APPROVED`-style `ENCRYPTION_UNAVAILABLE`), writes disabled; NEVER plaintext interim.
- If key management is not implemented, sensitive registration collection stays DISABLED: the create endpoint returns 403 `FEATURE_DISABLED`, and a test proves plaintext can never land in the column (write path requires ciphertext fields non-null — see §4 CHECK).
- Pack gating honesty: JO catalog `ACTIVE` is metadata. Initial executable capabilities are EMPTY (a dev-only synthetic test capability may exist, explicitly labeled, never counting as approval). AE/SA `PLANNED` with zero rules, no RUN affordance, no Jordan fallback — enforced in resolver + API + (future) worker paths. Resolver contract tests (capabilities, context validation, eligible-rules filtering with explicit skip reasons) are implementable and required NOW; financial-worker enforcement tests are marked NOT_TESTABLE until handlers exist (#35 prod gate). Catalog ACTIVE ≠ rule approval, stated in code comments and docs.
